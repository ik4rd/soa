# Архитектура маркетплейса

Проект описывает сервисы маркетплейса, их данные и взаимодействия. Сейчас реализован только каркас Orders на FastAPI: `/health` и запуск в Docker.

## Запуск

Команды требуется выполнить из корня репозитория:

```bash
docker compose up --build -d --wait
curl -i http://localhost:8080/health
```

Ожидаемый ответ:

```http
HTTP/1.1 200 OK
content-type: application/json

{"status":"ok"}
```

Swagger доступен по адресу [localhost:8080/docs](http://localhost:8080/docs)

```bash
docker compose ps           # состояние контейнера
docker compose logs orders # логи
docker compose down        # остановка
```

## Предположения и границы

1. Просмотр товаров и ленты будет происходить чаще оформления заказов. Предполагаем, что ленту придётся масштабировать отдельно от операций записи.
2. Каталог должен возвращать актуальную цену при оформлении. В ленте допустима небольшая задержка обновления карточек.
3. Ошибки email-провайдера не должны мешать оформлению заказа. Оплата зависит от внешней системы, поэтому её результат может прийти позже ответа пользователю.
4. Для первого бизнес-релиза принимаем одну валюту — RUB — и одного продавца в заказе. В заказе может быть несколько товаров. Комиссии, выплаты продавцам, скидки и налоги пока не рассматриваем.
5. Персонализация основана на выбранных пользователем категориях и прошлых покупках. Сначала показываем товары из интересующих категорий, внутри них сортируем по популярности за 30 дней. Для пользователя без истории используем общую популярность. Часть выдачи выделяем новинкам. Этого достаточно для первой версии без ML.
6. Уведомления отправляем по email. Логистику, складской учёт, резервирование, возвраты и модерацию оставляем за рамками проекта. В Catalog есть признак доступности товара, но нет гарантии наличия определённого количества на складе.

## Домены и сервисы

1. **Пользователи (Users).** Регистрация, вход, роли покупателя и продавца, контакты и интересы.
2. **Каталог (Catalog).** Создание и публикация товаров, категории, описания, цены и доступность.
3. **Лента (Feed).** Подбор и ранжирование карточек, учёт интересов и покупок, общая выдача для новых пользователей.
4. **Заказы (Orders).** Оформление, состав заказа, сохранение условий покупки и переходы между статусами.
5. **Платежи (Payments).** Расчёт суммы по полученным от Orders позициям, создание платежа у провайдера, обработка результата и учёт попыток оплаты.
6. **Уведомления (Notifications).** Шаблоны писем, отправка по событиям заказа, журнал доставки и повторные попытки.

Каждому домену соответствует отдельный сервис. Orders хранит, что и на каких условиях заказал покупатель. Payments рассчитывает сумму по этим условиям и учитывает оплату.

Feed отделён от Catalog из-за разных задач. Catalog принимает изменения продавцов и хранит актуальные предложения. Feed работает с копией карточек и обслуживает чтение. Изменение алгоритма выдачи не требует менять каталог или оформление заказа.

Notifications вынесен отдельно, чтобы задержки отправки писем не занимали ресурсы Orders. Users отвечает за учётную запись и роли, а права на конкретный товар или заказ проверяет владеющий им сервис.

## Владение данными

У каждого сервиса своя PostgreSQL и отдельная учётная запись для доступа к ней. Напрямую читать или изменять чужую БД нельзя. Данные другого домена получаем через API или события RabbitMQ.

Users хранит учётные записи, хеши паролей, роли, контакты и выбранные категории. Catalog хранит товары, их продавцов, категории, описания, цены и доступность.

Orders хранит позиции заказа, количество, покупателя и продавца, контакт для данного заказа, статусы и историю изменений. Названия и цены сохраняются на момент оформления: последующее редактирование товара не меняет условия уже созданного заказа.

Payments хранит расчёты, суммы в копейках, валюту, попытки оплаты, ключи идемпотентности и идентификаторы провайдера. Банковские карты обрабатывает провайдер; их данные в маркетплейсе не сохраняются.

Feed хранит копию опубликованных карточек, интересов пользователей и агрегаты покупок. Эти данные обновляются по событиям и могут отставать от Catalog и Users. Для первой версии достаточно PostgreSQL: отдельные поисковый движок и кэш пока не обоснованы требованиями.

Notifications хранит шаблоны, задания на отправку, контакт из заказа, результаты и число попыток. Изменение email в профиле не меняет контакт уже оформленного заказа. Контакты передаются только Notifications, в события для Feed они не включаются.

## Взаимодействие сервисов

Web App обращается к Users, Catalog, Feed и Orders по HTTPS с JSON. Users выдаёт подписанный токен, сервисы проверяют его подпись и права пользователя. Валидный токен продавца сам по себе не разрешает менять чужой товар. Ключ проверки распространяется заранее, поэтому каждый запрос не требует обращения к Users. Отзыв роли учитывается не позже истечения короткоживущего токена.

При оформлении Orders запрашивает контакт покупателя у Users и актуальные товары у Catalog. Затем передаёт снимок позиций в Payments и получает расчёт и ссылку на оплату. Эти вызовы синхронные: результат нужен, чтобы продолжить оформление. Служебные межсервисные операции недоступны из браузера.

Payments обращается к платёжному провайдеру по HTTPS, Notifications так же передаёт письма email-провайдеру. Покупатель оплачивает заказ на странице платёжного провайдера. Подтверждение приходит асинхронно через HTTPS webhook в Payments, который проверяет подпись отправителя. Возврат браузера на сайт не считается подтверждением оплаты.

События передаются через RabbitMQ по AMQP:

- Users публикует `UserPreferencesChanged`, Feed обновляет интересы пользователя.
- Catalog публикует `ProductChanged` и `ProductUnpublished`, Feed обновляет или убирает карточку.
- Payments публикует `PaymentSucceeded` и `PaymentFailed`, Orders учитывает результат попытки оплаты.
- Orders публикует `OrderPaid`, Feed обновляет историю покупок и популярность товаров.
- Orders публикует `OrderStatusChanged`, Notifications формирует письмо покупателю.

## Оформление и оплата заказа

Orders проверяет пользователя, получает контакт из Users, а цены и доступность — из Catalog. Если цена изменилась относительно показанной покупателю, нужно подтвердить новые условия. При недоступности обязательных сервисов оформление не продолжается.

Orders сохраняет позиции и цены в состоянии `pending_payment`. Затем Payments получает этот серверный снимок и рассчитывает сумму: цена каждой позиции в копейках умножается на количество, результаты складываются. Сумме, присланной браузером, сервис не доверяет. Payments сохраняет расчёт, создаёт платёж у провайдера и возвращает ссылку. Orders сохраняет сумму и идентификатор платежа, а пользователь переходит к оплате.

После webhook Payments проверяет подпись, сумму, валюту и допустимость изменения статуса. Результат сохраняется и публикуется в RabbitMQ. Orders сверяет успешный платёж со своим заказом, переводит его в `paid` и отправляет события для Feed и Notifications. Неуспешная попытка не делает заказ оплаченным; пользователь может начать новую попытку. Продавец через Orders меняет последующие статусы на `shipped` и `completed`, о чём покупатель также получает письма.

Общей транзакции между Orders, Payments и провайдером нет. При потере ответа операция могла уже завершиться, поэтому повтор использует тот же ключ идемпотентности. Новый ключ создаётся только для новой операции. Payments сверяет неопределённый результат с провайдером, Orders — с Payments. Поддержка таких ключей и поиска платежа по стабильному идентификатору — требование к выбору провайдера.

Изменение данных и предназначенное к отправке событие сохраняются одной транзакцией в БД сервиса — это transactional outbox. Фоновый отправитель передаёт событие брокеру и ждёт подтверждения. Получатель сохраняет идентификатор обработанного события вместе со своими изменениями: повтор не должен второй раз учитывать покупку или менять статус. Версия объекта позволяет не применять устаревшее обновление поверх нового.

Если событие об оплате пришло раньше, чем Orders сохранил ответ Payments, обработка откладывается до восстановления связи с расчётом. Зависшие заказы и платежи проверяются фоновым процессом сверки. При отказе брокера события остаются в outbox, лента и уведомления временно отстают.

Временные ошибки обрабатываются повторными попытками с увеличением интервала. После исчерпания попыток сообщение попадает в очередь ошибок для разбора. Сбой отправки письма не отменяет заказ. Если email-провайдер не поддерживает идемпотентность, при потере его ответа возможно повторное письмо.

## Варианты архитектуры

### Модульный монолит

Все шесть доменов можно разместить в одном приложении с отдельными модулями и схемами одной PostgreSQL. Это проще запускать, отлаживать и сопровождать. Связанные внутренние изменения можно выполнять одной транзакцией, между модулями нет сетевых ошибок.

Цена простоты — общий релиз и общий процесс. При росте нагрузки на ленту масштабируется всё приложение, а сбой одного модуля может затронуть остальные. Вызовы платёжного провайдера всё равно требуют отдельной обработки отказов: транзакция БД на него не распространяется. Для небольшой команды и ограниченного MVP этот вариант был бы предпочтительным.

### Три крупных сервиса

Другой вариант — объединить домены в Accounts (пользователи), Marketplace (каталог и лента) и Commerce (заказы, платежи и уведомления). У каждой группы своя БД.

Так меньше сетевых контрактов и развёртываний. Заказ и внутренний учёт платежа находятся рядом, товар и его выдачу проще согласовать. Но лента масштабируется вместе с каталогом, а обработка платежей и писем делит ресурсы с оформлением заказов. Компромисс — частичная независимость при меньших расходах на эксплуатацию.

### Шесть доменных сервисов — выбранный вариант

Вариант на диаграммах позволяет отдельно менять и масштабировать ленту, изолировать интеграции платежей и email, ограничивать доступ к данным каждого домена. Обновления сервисов можно выпускать независимо при сохранении совместимости API и событий.

За это приходится платить количеством приложений и БД, сетевыми задержками и временным расхождением данных. Нужны обработка повторов, сверка платежей, общие логи, метрики и отслеживание запросов между сервисами. Оформление зависит от доступности нескольких API.

Для целевой архитектуры выбираем это разделение из-за разной нагрузки и требований к отказам: Feed обслуживает чтение, Catalog хранит актуальное предложение, Orders фиксирует условия покупки, Payments учитывает деньги, Notifications доставляет сообщения. Отдельные владельцы данных и независимое изменение этих частей здесь важнее простоты развёртывания. В рамках задания запускается только каркас одного сервиса, поэтому поднимать все шесть сервисов, базы и брокер сейчас не требуется.
